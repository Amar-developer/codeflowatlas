# Acceptance criteria

The first useful product demonstration is accepted when a learner can submit a supported public GitHub or Bitbucket URL for a small FastAPI fixture, pin its revision, and analyze its source without executing it; select an endpoint; follow its route, handler, functions, detectable database access, and response in an interactive flow graph or mind map; click supported nodes and edges to open file and line evidence; and ask an integrated AI guide about a selected step. The guide must cite inspected source, distinguish resolved from inferred or unknown relationships, and work without a running application or database. A text step view must provide the essential path, and unsupported files and incomplete paths must be visible. Fixture expectations, API contracts, and the user flow must pass automated tests in CI.

The planned visualization and query capabilities are accepted when a supported fixture lets the learner move from repository overview to a feature path and function calls without losing the pinned revision or source links. A natural-language question returns relevant file-and-line excerpts and an evidence-backed focused graph, or clearly states that the evidence is missing. Live suggestions are editable and project-scoped. A diagram export retains the visible title, revision, legend, and unresolved edges, with an accessible text outline. An optional LLM prompt draft shows the exact authorized, secret-filtered evidence before the learner copies or sends it. Fixture and UI checks must verify these outcomes.

The later full-stack source-flow demonstration is accepted when a paired React or Next.js and FastAPI fixture lets a learner select one frontend action and follow a statically resolvable HTTP call to its backend route, downstream functions, and response handling. The graph must open evidence at the frontend call site and backend route, identify analyzer versions and capability levels, and show dynamic URLs, unmatched calls, and frontend-only or backend-only paths as incomplete. Fixture expectations and the visible graph must agree. This source-flow result does not imply runtime or test-lab support for the frontend framework.

The runtime diagnosis demonstration adds an approved isolated target with a disposable database built from validated models, migrations, or fixtures and synthetic seed records. It produces a trace waterfall with real request and sanitized database timings, observed errors, and an evidence-backed explanation of one issue and a testable improvement. No original or production database, credentials, or data dump is used. The AI test bot demonstration proposes one reviewable student journey with explicit target, actions, synthetic inputs, assertions, request and time limits, then a deterministic runner executes it and produces replayable request and trace evidence. Missing schema or dependencies result in an explicit unsupported state, not a fabricated run. The optional system design lab adds charts for a saved baseline, bounded 100-concurrent-virtual-user scenario, one bounded dependency fault, measured findings, and a reproducible before/after comparison on the same synthetic dataset and environment. A source-only result must never claim measured behavior, and an AI suggestion must never be presented as a verified fix until a comparable run tests it.

Additional framework, language, infrastructure, or AI capabilities are complete only when their own fixtures, safety checks, and user-facing evidence meet the same standard. Resume and interview claims should reflect behavior and measurements actually demonstrated by the project.
