# Acceptance criteria

The first useful product demonstration is accepted when a learner can submit a supported public GitHub or Bitbucket URL for a small FastAPI fixture, pin its revision, and analyze its source without executing it; select an endpoint; follow its route, handler, functions, detectable database access, and response in an interactive flow graph or mind map; click supported nodes and edges to open file and line evidence; and ask an integrated AI guide about a selected step. The guide must cite inspected source, distinguish resolved from inferred or unknown relationships, and work without a running application or database. A text step view must provide the essential path, and unsupported files and incomplete paths must be visible. Fixture expectations, API contracts, and the user flow must pass automated tests in CI.

The runtime diagnosis demonstration adds an approved isolated target, a trace waterfall with real request and sanitized database timings, observed errors, and an evidence-backed explanation of one issue and a testable improvement. The optional system design lab adds charts for a saved baseline, bounded 100-concurrent-virtual-user scenario, one bounded dependency fault, measured findings, and a reproducible before/after comparison. A source-only result must never claim measured behavior, and an AI suggestion must never be presented as a verified fix until a comparable run tests it.

Additional framework, language, infrastructure, or AI capabilities are complete only when their own fixtures, safety checks, and user-facing evidence meet the same standard. Resume and interview claims should reflect behavior and measurements actually demonstrated by the project.
