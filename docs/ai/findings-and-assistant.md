# Findings and AI assistant

The findings engine is deterministic before any AI interpretation. Initial rules include dominant cumulative or exclusive span duration, repeated database calls, high error concentration, and p99 growth under load. Later rules can cover queue lag, pool saturation, cache misses, and retry amplification. A finding contains rule ID and version, severity, evidence IDs, sample size, comparison window, measured values, uncertainty, and a plain-language conclusion. A finding such as “database spans represented 78% of measured request duration across 1,000 traces” is valid only when those records exist.

The AI assistant accepts a constrained evidence bundle: repository metadata, selected source snippets, IR paths, endpoint details, trace summaries, metrics, findings, and relevant documentation. It can explain a request path, observed bottleneck, likely causes, test ideas, and architecture tradeoffs. It must label observations, inferences, and unknowns separately. It cannot claim a function ran merely because a static edge exists.

The AI test bot is a separate planned capability. It proposes a finite student-like API or browser journey from the selected revision's discovered endpoints, schemas, and fixtures, plus synthetic accounts and records. Its output is a scenario proposal, not authority to execute arbitrary actions. The learner reviews the target, state-changing steps, assertions, maximum requests, rate, duration, and synthetic dataset. A deterministic runner freezes and validates that plan, executes it only against the isolated disposable target, and emits actual responses, checks, traces, and a replayable issue report. AI may explain those records; a suspected root cause remains a hypothesis until supported by a comparable test. If the target schema or dependencies cannot be validated, the bot reports unsupported setup rather than inventing results.

Source-only AI help includes selected-node explanation, value-flow questions, and uncertainty-aware walkthroughs. Later learning exercises can ask a student to predict behavior before showing code or trace evidence. Flow-diff explanations must separate changed source paths from measured behavioral changes. Bound context to the selected endpoint and revision to control cost and reduce unrelated or sensitive data exposure.

Natural-language code queries should resolve to the current project's revision, relevant IR entities, and bounded source excerpts. Return an evidence-linked answer and a focused visualization or code snippet when supported. Live query suggestions can come from the endpoint/entity catalog and curated examples without sending every keystroke to a model. Suggestions identify possible questions; they never assert that a path is verified. If retrieval finds no reliable evidence, explain the gap instead of generating a plausible diagram.

An optional LLM prompt draft packages the selected question, limited source excerpts, graph context, revision ID, citations, and an instruction to state uncertainty. The learner sees and may edit the exact draft before copying it or choosing a configured model. Apply project authorization and secret filtering first. A model's response remains an explanation or hypothesis until the cited source or runtime evidence supports its claims.

Retrieval can index README files, architecture documentation, selected source ranges, endpoint descriptions, and findings using metadata including project ID, revision SHA, path, line range, entity ID, and document type. Secret scanning and access checks run before indexing and retrieval. Embeddings and a vector store are optional until keyword or structured retrieval proves insufficient.
